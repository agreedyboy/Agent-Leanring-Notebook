## Workflow
$ 文中所介绍的workflow主要有5种 $

---

### Prompt chaining
$ 工作流：提示流 $

其是将一个任务分解为一系列的任务，使用多个 LLM 串行完成这一系列任务，每个LLM 接收前一个LLM 的输出
在这个串行完成任务的过程中，可以手动设置一些门控例如判断当前这步有没有完成一个指定的任务，如果完成了就交给下一个LLM 继续进行处理，如果没有就直接退出或者执行什么其他的任务，我的理解是，这个门控可以根据当前任务的完成情况，将其交给后续不同的已经设定好的LLM 继续执行任务

---

$ 应用场景 $

任务是可以分成不同步骤执行的，例如:首先生成一个文案，然后将其翻译成英文


---

### Routing
$ 工作流：路由 $

顾名思义，其像路由器一样，可以将一个任务指定分配给不同的 LLM 去执行，这个分配的任务也是由一个 LLM 来执行的，
这个不同的用于解决任务的 LLM 是提前设定好的，只能较好地处理一些指定的任务（由于设置了不同的prompt），
因此这就需要任务是可以被互斥分解的（不是将任务分解，而是将这个任务分配到不同的类别中去），分解的关注点也需要找好，使任务被分配的准确率更高一些，而且输出的结果直接就是 LLM 的结果，
并不由其他 LLM 对于该结果进行总结等等操作

---

$ 应用场景 $

例如，可以通过用一个小 LLM 对我当前的任务的难度进行判断，如果任务难度较高，则交给能力更强同时成本更高的 LLM 去处理，
如果任务难度较低，则交给能力稍弱但是成本更低的 LLM 去处理，这样能够很好的控制成本

又或是对用户的输入进行判断，判断其是需要进行代码功能核查还是需要代码改错还是需要代码优化等不同任务，然后交由不同的 LLM 去处理（因为不同LLM 有不同的擅长点）

---

### Parallelization
$ 工作流：并行化 $

当任务可以拆分为不同的可以同时进行执行的子任务时，可以使用该方法，该方法并行通过多个 LLM 来处理多个子任务，然后由一个 Aggregator 来汇总结果并输出，这样可以使任务处理更加高效迅速。

---

$ 应用场景 $

例如让一个模型实例处理用户查询，同时另一个实例筛查其中是否包含不当内容或请求。这种方法通常比让同一个 LLM 调用同时处理防护措施和核心响应效果更好

## When to use Workflow

在我看来，如果一个任务是可以提前预测出 LLM 解决其所需要步骤以及每个步骤中 LLM 会完成什么任务，那么这个任务就是可以用 Workflow 来解决，例如有一个任务是需要生成一个报告并且需要翻译成英文，、这个任务很明显可以分解为两步，首先生成一个符合要求的报告，然后将其翻译成英文，这两步子任务都可以判断出是可以直接分别使用两个针对性的 LLM 来完成任务，并且完成这个任务的步骤与完成条件判断是可知的，因此这个任务就可以使用 Workflow，而不是引入较为复杂的Agent，即当一个任务是较为简单的、可拆分、可预测的或者说是解决路径是可硬编码的，那么其就可以尝试使用 Workflow；因为这些任务是相对简单、有结构的，通过固定的设计来安排就可以很好地完成任务。

Workflow 与 Agent 还有一个很关键的区别，Workflow 在完成任务时并不会再寻求外界的信息或者是用户的输入，而 Agent 在执行任务时，当遇到需要用到的而其本身不确定的信息时，会主动使用 Tools 来获取对应的信息或者是请求用户的输入，而且 Agent 可以自行判断当前任务是否已经执行完成，而不需要提前设定好哪步哪步需要执行几次等

---

## When to use Agent

智能体适用于哪些难以或无法预测所需步骤数量、且无法硬编码固定路径的开放式问题；或是在解决问题的过程中，需要使用到一些外部的信息

---

## Difference between Agent and Multi-Agent

Agent 只使用一个 LLM 来处理所有的任务包括理解业务目标、记忆历史、选择合适工具并调用等任务，面对复杂任务时，随着任务的推进，会使上下文的prompt变得非常臃肿，导致模型对任务的处理能力下降，而且其缺乏对抗或者审视机制，容易出现在错误的逻辑链条上陷入自我合理化的死循环

Multi-Agent 使用多个 LLM 来进行角色扮演，每个 Agent 维护自己的历史上下文，但是其相对较为复杂，而且需要 Agent 之间存在较为明确、高校的通信协议，且任务本身应该是可以通过角色分工与群体协作来解决的
